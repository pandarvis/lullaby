# Lullaby V0 Windows — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for the recommended sequential execution, or superpowers:subagent-driven-development if the user selects delegation. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Livrer une application Iris permettant de développer dans un dossier avec
Claude ou Codex via les abonnements existants, puis de reprendre la session native.

**Architecture:** Electron main possède les projets, sessions, adaptateurs et
processus. Un preload limité alimente React et assistant-ui depuis un état externe.
Les moteurs restent propriétaires du contexte ; le stockage Lullaby est une projection.

**Tech Stack:** Electron, React, TypeScript, electron-vite, assistant-ui,
Claude Agent SDK, Codex App Server, Node fs/child_process, JSON local ;
Vitest pour les contrats et electron-builder pour le paquet Windows proposés.

**Spec:** [V0 Windows](../specs/2026-09-26-v0-windows-design.md),
[fidélité aux moteurs](../../fidelite-moteurs.md),
[feuille de route](../../feuille-de-route.md).

Statut : plan validé. T1–T6 implémentés et intégrés à develop ;
T7 : paquet construit, relecture corrigée, recette complète encore ouverte.
Les cases constituent la checklist initiale ;
les preuves exécutées et les réserves sont dans [l'état du projet](../../etat-projet.md)
et les recettes liées. Les scripts npm ci-dessous existent désormais.

## Global Constraints

- Windows natif, Electron, aucun Docker ou WSL, aucune clé API facturée requise.
- Minimum de composants à installer et réutilisation du chat.
- Le choix du fournisseur est fixé pour une conversation.
- Une seule exécution à la fois par dossier.
- Pont preload limité et typé ; aucun accès direct aux SDK depuis la fenêtre React.
- Stockage JSON local versionné, écrit atomiquement par le processus principal.
- Ne pas saisir ni recopier les jetons dans l'interface Lullaby.
- Préserver Iris et le symbole `em-lullaby` de la maquette ; icônes SVG.
- Notifications Windows exclues de cette tranche ; aucune API cloud de chat ajoutée.
- Doc, recette et commits par tâche ; aucune fusion/release automatique.

## Review Focus

1. Chemins Windows avec espaces/accents, alias du même dossier : T2 vérifie
   l'identité canonique et le verrou avant de lancer un deuxième agent.
2. Autorisation périmée ou réponse sur la mauvaise session : T2 refuse sans
   transmettre au moteur ; T5 rend l'état compréhensible.
3. Arrêt brutal pendant une écriture/une génération : T2 conserve un état valide
   et marque le tour interrompu ; T7 vérifie après redémarrage du paquet.
4. Variable ou configuration native pouvant choisir une facturation API : T3/T4
   interdisent l'appel ambigu et montrent le diagnostic sans exposer de valeur.
5. Démarrage possible mais moteur enfant bloqué ou proxy muet : T6/T7 différencient
   disponibilité du processus, port joignable et échange réel.

## Contrats communs à créer en T1/T2

Dans `src/shared/contracts.ts` (les identifiants sont des UUID Lullaby, sauf `nativeId`) :

```ts
export type Provider = 'claude' | 'codex';
export type Phase = 'idle' | 'running' | 'waiting' | 'done' | 'interrupted' | 'error';
export type Project = { id: string; name: string; cwd: string; folderKey: string };
export type LaunchChoices = { model?: string; effort?: string; permissionProfile?: string };
export type Session = {
  id: string; projectId: string; provider: Provider; title: string;
  nativeId?: string; phase: Phase; draft: string; choices: LaunchChoices;
};
export type PromptRequest = { sessionId: string; text: string };
export type ReplyRequest = {
  sessionId: string; runId: string; requestId: string;
  answer: { kind: 'allow' | 'deny' } | { kind: 'text'; text: string };
};
export type EventBody =
  | { kind: 'bound'; nativeId: string }
  | { kind: 'text'; itemId: string; mode: 'append' | 'replace'; text: string }
  | { kind: 'action'; itemId: string; label: string; state: 'running' | 'done' | 'error'; detail: string }
  | { kind: 'request'; requestId: string; requestKind: 'approval' | 'question'; text: string }
  | { kind: 'state'; phase: Phase }
  | { kind: 'error'; code: string; message: string };
export type SessionEvent = {
  sessionId: string; runId: string; eventId: string; body: EventBody;
};
export type ChatItem = {
  id: string; role: 'user' | 'assistant'; text: string;
  actions: { id: string; label: string; detail: string; state: 'running' | 'done' | 'error' }[];
};
export type Snapshot = {
  revision: number; projects: Project[]; sessions: Session[];
  messages: Record<string, ChatItem[]>; pending: SessionEvent[];
};
export type Diagnostic = {
  provider: Provider; available: boolean; version?: string;
  auth: 'subscription' | 'missing' | 'ambiguous'; issues: string[];
  skills: { name: string; available: boolean; evidence: string }[];
};
export type NetworkProfile = {
  provider: Provider; proxyUrl?: string; certificatePath?: string;
  launcher?: { executable: string; args: string[]; host: string; port: number };
};
export type ProxyState = 'stopped' | 'starting' | 'owned' | 'external' | 'error';
export type Result<T> = { ok: true; value: T } | { ok: false; code: string; message: string };
```

Dans `src/main/providers/types.ts`, types utilisés par T2–T4 :

```ts
import type { Diagnostic, EventBody, LaunchChoices, Provider, ReplyRequest } from '../../shared/contracts';
export type RunInput = {
  cwd: string; nativeId?: string; text: string; choices: LaunchChoices;
  env: Record<string, string | undefined>;
};
export type ProviderRun = {
  events: AsyncIterable<{ eventId: string; body: EventBody }>;
  reply(requestId: string, answer: ReplyRequest['answer']): Promise<void>;
  interrupt(): Promise<void>;
  close(): Promise<void>;
};
export interface ProviderAdapter {
  provider: Provider;
  diagnose(cwd: string): Promise<Diagnostic>;
  run(input: RunInput): Promise<ProviderRun>;
}
```

Le catalogue détaillé des outils reste propre à chaque moteur : ce contrat ne
limite pas ses outils aux variantes affichées. Une donnée non représentable est
signalée explicitement et conserve un détail textuel lisible. Une demande qui ne
peut pas recevoir de réponse correcte n'est jamais approuvée automatiquement.
